# AstraLink

**Track every launch. Understand every mission.**

[Live demo](https://astralink-pi.vercel.app)

AstraLink is a space launch tracker that goes beyond raw schedules. It computes historical reliability scores for launch agencies and rocket families, tracks status changes across syncs, and generates AI-powered mission briefings for every upcoming launch using the Anthropic API.

## What it does

AstraLink ingests upcoming and historical launch data from Launch Library 2, stores it in PostgreSQL, and derives analytical intelligence from it: agency success rates, rocket family reliability histories, and average scrub frequencies. Each launch detail page surfaces this context alongside an on-demand mission briefing generated by Claude Haiku and cached after the first generation.

Users can register, follow launches, and view their personal launch dashboard. The frontend is a SpaceX-inspired React interface with full filtering, pagination, and agency and rocket family profile pages.

## Architecture

```text
React + TypeScript             Django REST API                  PostgreSQL
Vercel                         Railway                          Railway
┌──────────────┐   HTTPS       ┌──────────────────┐   SQL       ┌─────────────────┐
│ AstraLink UI │ ────────────> │ AstraLink API    │ ──────────> │ launches        │
│              │               │                  │             │ agency_stats    │
└──────────────┘               └────────┬─────────┘             │ rocket_stats    │
                                        │                       │ mission_briefings│
                                        │                       └─────────────────┘
                               ┌────────┴─────────┐
                               │ Launch Library 2 │
                               │ Anthropic API    │
                               └──────────────────┘
```

The API exposes paginated, filterable launch endpoints backed by a PostgreSQL database populated via management commands. Analytics are computed from historical launch data and stored separately. Mission briefings are generated lazily on first request and served from cache on subsequent visits.

## Notable engineering decisions

### Derive intelligence from raw data

Fetching and displaying API data is table stakes. AstraLink goes further by computing aggregated statistics from 700+ historical launches: success rates per agency and rocket family, average number of status changes before liftoff, and most common orbit and mission type per provider. This derived layer is what makes the backend interesting — it is not a passthrough.

### Lazy briefing generation with persistent caching

Mission briefings are generated on the first visit to a launch detail page and cached in the database. Subsequent visits read from the cache with no API call. This keeps costs negligible, avoids unnecessary generation for launches nobody visits, and demonstrates an understanding of cost-aware AI integration.

### Status change tracking on every sync

Each time `fetch_launches` runs, it compares incoming launch statuses against stored values and records any change in a `LaunchStatusHistory` table. This makes scrub and delay patterns queryable and feeds the average status changes metric surfaced in reliability panels.

### Backfill instead of re-fetch

When the `launch_success` derivation logic was corrected post-ingestion, a `backfill_launch_success` command re-derived truth from already-stored `status` fields rather than re-fetching 700 launches from a rate-limited API. Keeping the fix offline reduced risk and respected the upstream rate limit.

### Split database strategy

Django's built-in auth system (users, sessions) runs on PostgreSQL alongside the application data. MongoEngine was evaluated and prototyped as a document store for the launch layer, but the operational complexity of the hybrid setup and Atlas M0 timeout behavior outweighed the flexibility benefits at this scale. PostgreSQL handles all data cleanly with the existing Django ORM.

## Features

- **Launch list** — paginated upcoming launches with search and filters (provider, rocket family, orbit, mission type)
- **Launch detail** — full mission data, launch window, reliability panel, and AI mission briefing
- **Agency profiles** — per-agency stats (total launches, success rate, avg status changes, common orbit) and launch history
- **Rocket family profiles** — same analytics grouped by rocket family
- **Reliability scores** — surfaced on every launch card and detail page from precomputed historical data
- **Mission Briefing** — on-demand, Claude Haiku-generated briefing cached after first generation
- **Auth** — registration, login, logout with Django session authentication
- **Follow system** — follow and unfollow launches, personal dashboard

## Known limitations

- Authentication does not work on mobile Safari or Chrome due to cross-domain cookie restrictions (Safari ITP). Desktop browsers work correctly. Resolving this requires same-domain deployment or a JWT-based auth flow.
- Launch Library 2's free tier enforces strict rate limits. The `fetch_historical_launches` command may be interrupted and resume on retry after a cooldown period.
- The production database is populated manually via management commands. There is no automated scheduled sync — this is intentional to avoid unnecessary Railway compute.

## Local setup

### Prerequisites

- Python 3.12+
- Node.js 20+ and npm
- PostgreSQL 16 or SQLite for local development

### Backend

```bash
cd astra_link

python -m venv astralink
source astralink/bin/activate
pip install -r requirements.txt
```

Create a `.env` file at the project root:

```env
SECRET_KEY=your-django-secret-key
DEBUG=True
ANTHROPIC_API_KEY=your-anthropic-api-key
```

Apply migrations and populate data:

```bash
python manage.py migrate
python manage.py fetch_launches
python manage.py fetch_historical_launches
python manage.py backfill_launch_success
python manage.py compute_stats
```

The API listens on `http://localhost:8000`.

### Frontend

```bash
cd frontend
npm install
npm run dev
```

Vite serves the frontend at `http://localhost:5173` and proxies `/api` requests to Django on port 8000.

For a production build:

```bash
cd frontend
npm run build
```

## Data population commands

| Command | Description |
|---|---|
| `fetch_launches` | Fetches upcoming launches from Launch Library 2 |
| `fetch_historical_launches` | Fetches historical launches from Launch Library 2 |
| `backfill_launch_success` | Derives `launch_success` from stored status fields |
| `compute_stats` | Computes agency and rocket family reliability stats |

Run these in order after a fresh database setup.
